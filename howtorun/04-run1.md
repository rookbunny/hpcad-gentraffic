# How To Run: Run1 (Opportunistic Intruder)

## Purpose

- Capture the benign scaffold underneath a loud, opportunistic attack.
- The window is as long as the attack needs: `run1` has no timer, so the capture runs until you stop it by typing `exit`. At a 15 second bucket span, 20 minutes is 80 buckets if you want a length comparable to earlier runs.
- The only systematic difference from the baseline is the attack itself, so the benign substrate is generated the same way and every attacker action is logged as it happens.

## Processes in this profile

- `chat_ws`
- `healthcheck`
- `email`
- `prom_scrape` (runs on the monitoring VM)

Note that `run1` omits the `noaa` space-weather pulls that appear in `baseline` and `run2`. The window is short and the attack is loud, so the long external transfer is left out.

## What is not generated here

- The C2 beacon is hand-run in the C2 framework, not by this generator.
- Manual actions (brute force, privilege escalation, C2 interaction) are performed by the operator and recorded with `log_user.py`.
- Zabbix. That stream is real: the `zabbix-agent` daemon on the honeypot produces it, and `zabbix_log.py` captures it at the packet level into `<tag>_zabbix.pcap` and `<tag>_knownzabbix.json`, folded into the benign and all-traffic unions. `run_capture.sh` starts and stops it with the run.
- The attack traffic itself. `attacker_log.py` captures every packet to or from `addresses.attacker_ip` at the packet level into `<tag>_attacker_traffic.pcap` and `<tag>_attacker_traffic.json`, folded into the all-traffic union but never into the benign or user unions. `run_capture.sh` starts and stops it with the run. This is packet-level labeling and it does **not** replace `log_user.py`: the packets say what crossed the wire, your notes say what you were doing.

**Before starting, confirm `addresses.attacker_ip` in `config.yaml` is the address you will actually attack from.** If it is wrong, the attack still lands in `<tag>.pcap` but nothing labels it, and the run is not usable as ground truth. Re-run `SETUP.sh` if it has changed.

```bash
./.venv/bin/python3 attacker_log.py --print-filter --iface ens19 \
    --run-dir /tmp --tag R0000-S00000
```

## Steps

1. On the capture host, start the run with a fresh seed. The script prints the run id, the tag, and the seed.

   ```bash
   sudo ./run_capture.sh run1 ens19
   ```

   `run_capture.sh` writes the active tag to `.current_run`, so `log_user.py` picks it up automatically for the rest of the run.

2. On the monitoring VM, start the scrape process with the same seed and run id.

   ```bash
   ./.venv/bin/python3 gen.py --profile run1 --role promsvc \
       --seed <seed> --run-id <run_id>
   ```

3. As the opportunistic attack proceeds, record each attacker action the moment it happens. The tag is read from `.current_run`, so it does not need to be passed. Add an ATT&CK id with `--phase` where one applies.

   ```bash
   ./.venv/bin/python3 log_user.py "hydra ssh brute force start" --source attacker --phase T1110
   ./.venv/bin/python3 log_user.py "valid ssh login gained"       --source attacker --phase T1078
   ./.venv/bin/python3 log_user.py "sliver interactive shell open" --source attacker
   ```

4. When the attack is done, stop the capture by typing `exit` into the terminal running `run_capture.sh` (Ctrl-C also works).

   ```bash
   exit
   ```

   The generator finalizes its manifest with the real elapsed time, tcpdump flushes, and a summary prints: every expected file with its packet or record count, how long the capture ran, and a closing line that is either `all expected files were written successfully` or a list of problems. Read it before tearing down the range; the script also exits non-zero when something is wrong.

## Reseeding

- `run1` uses a seed distinct from `baseline` and `run2`. To reproduce an earlier `run1`, pin its seed.

  ```bash
  sudo ./run_capture.sh run1 ens19 24680
  ```

## Outputs

Under `logs/<tag>_logs/`, where the tag is `R<run_id>-S<seed>`:

- `<tag>.pcap` (the whole wire)
- `<tag>_zabbix.pcap` (the real Zabbix agent's packets on their own)
- `<tag>_attacker_traffic.pcap` (every packet to/from the attacker address, on its own)
- `<tag>_knownbenign.json` (scripted benign events plus one record per Zabbix packet)
- `<tag>_knownuser.json` (attacker actions logged during the run)
- `<tag>_knownzabbix.json` (the Zabbix stream on its own, a subset of the benign union)
- `<tag>_attacker_traffic.json` (one record per attacker packet — its own class, in `alltraffic` only)
- `<tag>_alltraffic.json` (union of all three classes, keyed by the `class` field)
- `<tag>.zabbix.meta.json` (the Zabbix filter, addresses, counts, and stop reason)
- `<tag>.attacker.meta.json` (the attacker filter, address, counts, and stop reason)
- `<tag>.<role>.manifest.json`

Within the run window only the scripted benign set, the real Zabbix stream, the recorded manual actions, and the adversary are present. The adversary's packets are now labeled directly, so any packet not attributable to a benign, Zabbix, user, or attacker record is residue worth looking at rather than an assumption.

## Verification checklist

- The closing summary reports every expected file as `OK`, with a non-zero packet count and non-zero benign record count.
- The manifest reports `elapsed_seconds` and `actual_buckets` matching the window you actually ran, and `stopped_by` naming how it ended. `expected_buckets` is null for an untimed profile, which is expected.
- Every attacker action taken during the window has a matching record in `<tag>_knownuser.json` with `class=user`.
- The Zabbix line in the summary shows a non-zero packet count, and the pcap and log counts match. `zabbix: DISABLED` means `config.yaml` is missing the Zabbix addresses and the run has no Zabbix ground truth.
- **The attacker line in the summary shows a non-zero packet count**, and the pcap and log counts match. An `EMPTY during profile run1` warning means the attack was not captured: check that `addresses.attacker_ip` is the address you actually worked from. `attacker: DISABLED` is reported as a problem and the run exits non-zero — that run cannot be labeled.
- The record arithmetic holds: `knownbenign + knownuser + attacker_traffic == alltraffic`. The summary flags it as a `record mismatch` if it does not.
- The capture host and the monitoring VM share the same tag.
- The bucket span is 15 seconds, matching the baseline that this run is scored against.
