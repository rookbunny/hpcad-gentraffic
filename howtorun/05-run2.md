# How To Run: Run2 (Covert Long-Dwell Operator)

## Purpose

- Capture the benign scaffold underneath a covert, low-and-slow adversary.
- The window is as long as the dwell needs: `run2` has no timer, so the capture runs until you stop it by typing `exit`. At a 15 second bucket span, 40 minutes is 160 buckets if you want a length comparable to earlier runs. A covert beacon needs enough check-ins to establish a rhythm, so err long.
- Live web browsing is run during this window as cover, so the covert C2 rhythm has realistic human traffic to hide inside.

## Processes in this profile

- `chat_ws`
- `healthcheck`
- `email`
- `noaa` (external space-weather archive pulls)
- `prom_scrape` (runs on the monitoring VM)

## What is not generated here

- The C2 beacon is hand-run in the C2 framework at its covert cadence, not by this generator.
- Manual web browsing and every attacker action are performed by the operator and recorded with `log_user.py`.
- The attack traffic itself is captured at the packet level by `attacker_log.py` into `<tag>_attacker_traffic.pcap` and `<tag>_attacker_traffic.json` — every packet to or from `addresses.attacker_ip`, folded into the all-traffic union but never into the benign or user unions. `run_capture.sh` starts and stops it with the run.

## Zabbix and the impersonated service account

- The Zabbix stream in this run is real. Nothing generates it: the `zabbix-agent` daemon on the honeypot is the only source, and `zabbix_log.py` captures it into `<tag>_zabbix.pcap` and `<tag>_knownzabbix.json` while folding those records into the benign and all-traffic unions.
- The covert operator impersonates the Zabbix service account, so the Zabbix filter deliberately excludes the attacker address configured in `config.yaml`. Adversary traffic on the Zabbix ports is therefore never labeled as benign telemetry. It is captured and labeled as attacker traffic instead: those packets land in `<tag>_attacker_traffic.pcap` and `<tag>_attacker_traffic.json`, which is the clean split this run exists to produce — same ports, same service account, opposite label.
- That only works if the attacker address in `config.yaml` is the one actually used during the run. If the operator works from a different address than `SETUP.sh` was given, re-run `SETUP.sh` before the capture, or the impersonated traffic will land in the benign Zabbix log and nothing will label it as the adversary's. Confirm the filter before you start:

  ```bash
  ./.venv/bin/python3 attacker_log.py --print-filter --iface ens19 \
      --run-dir /tmp --tag R0000-S00000
  ```

- Comparing `<tag>_attacker_traffic.json` against `<tag>_knownzabbix.json` after the run is the direct way to see the impersonation: both are packet records on the same ports, separated only by which address they came from.

  ```bash
  ./.venv/bin/python3 log_user.py "zabbix service account impersonation" --source attacker --phase T1078
  ```

## Per-destination periodicity reminder

- The beacon, the real Zabbix agent stream, and the healthcheck all share roughly a 60 second cadence by design.
- Detection features must group flows by responder (destination IP, or IP plus port) before computing inter-arrival and periodicity, so the unit of analysis is `(destination, window)` rather than `window`. Aggregated per bucket, the three 60 second streams sum into one signal and the beacon hides. Computed per destination, the beacon surfaces as its own periodic endpoint.

## Steps

1. On the capture host, start the run with a fresh seed. The script prints the run id, the tag, and the seed, and writes the active tag to `.current_run`.

   ```bash
   sudo ./run_capture.sh run2 ens19
   ```

2. On the monitoring VM, start the scrape process with the same seed and run id.

   ```bash
   ./.venv/bin/python3 gen.py --profile run2 --role promsvc \
       --seed <seed> --run-id <run_id>
   ```

3. Run live browsing as cover during the window. Route an operator browser through an SSH dynamic proxy into the honeypot so the browsing egresses from the honeypot uplink and reaches the mirror. See the testing document for the tunnel setup.

   ```bash
   ssh -D 1080 -N operator@<honeypot_ip>
   ./.venv/bin/python3 log_user.py "youtube session start" --source browsing
   # browse for several minutes through the proxied browser
   ./.venv/bin/python3 log_user.py "youtube session stop"  --source browsing
   ```

4. Record each covert attacker action as it happens. The tag is read from `.current_run`. Add an ATT&CK id with `--phase` where one applies.

   ```bash
   ./.venv/bin/python3 log_user.py "beacon check-in observed"      --source attacker
   ./.venv/bin/python3 log_user.py "credential access via service" --source attacker --phase T1078
   ```

5. When the dwell is done, stop the capture by typing `exit` into the terminal running `run_capture.sh` (Ctrl-C also works).

   ```bash
   exit
   ```

   The generator finalizes its manifest with the real elapsed time, tcpdump flushes, and a summary prints: every expected file with its packet or record count, how long the capture ran, and a closing line that is either `all expected files were written successfully` or a list of problems. Read it before tearing down the range; the script also exits non-zero when something is wrong.

## Reseeding

- `run2` uses a seed distinct from `baseline` and `run1`. To reproduce an earlier `run2`, pin its seed.

  ```bash
  sudo ./run_capture.sh run2 ens19 13579
  ```

## Outputs

Under `logs/<tag>_logs/`, where the tag is `R<run_id>-S<seed>`:

- `<tag>.pcap` (the whole wire)
- `<tag>_zabbix.pcap` (the real Zabbix agent's packets on their own)
- `<tag>_attacker_traffic.pcap` (every packet to/from the attacker address, on its own)
- `<tag>_knownbenign.json` (scripted benign events plus one record per Zabbix packet)
- `<tag>_knownuser.json` (browsing and attacker actions logged during the run)
- `<tag>_knownzabbix.json` (the Zabbix stream on its own, a subset of the benign union)
- `<tag>_attacker_traffic.json` (one record per attacker packet — its own class, in `alltraffic` only)
- `<tag>_alltraffic.json` (union of all three classes, keyed by the `class` field)
- `<tag>.zabbix.meta.json` (the Zabbix filter, addresses, counts, and stop reason)
- `<tag>.attacker.meta.json` (the attacker filter, address, counts, and stop reason)
- `<tag>.<role>.manifest.json`

## Verification checklist

- The closing summary reports every expected file as `OK`, with a non-zero packet count and non-zero benign record count.
- The manifest reports `elapsed_seconds` and `actual_buckets` matching the window you actually ran, and `stopped_by` naming how it ended. `expected_buckets` is null for an untimed profile, which is expected.
- Browsing sessions and covert attacker actions all appear in `<tag>_knownuser.json` with `class=user`.
- The Zabbix line in the summary shows a non-zero packet count and a filter that excludes the attacker address actually used during the run.
- **The attacker line in the summary shows a non-zero packet count**, and the pcap and log counts match. An `EMPTY during profile run2` warning means the covert traffic was not captured — almost always the wrong `addresses.attacker_ip`. `attacker: DISABLED` is a problem and the run exits non-zero.
- The impersonated Zabbix packets appear in `<tag>_attacker_traffic.json` (with `dport` 10050/10051) and **not** in `<tag>_knownzabbix.json`. This is the single most important check in this run.
- The record arithmetic holds: `knownbenign + knownuser + attacker_traffic == alltraffic`.
- The proxied browsing shows up on the mirror as flows sourced from the honeypot.
- The capture host and the monitoring VM share the same tag.
- The bucket span is 15 seconds, matching the baseline that this run is scored against.
